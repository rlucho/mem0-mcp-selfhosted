# Collections (id 14) restructure — ProjeQtor V11.1.3 CSV import kit

Rebuilds **Banking > Collections** from 11 flat activities into a
`Country > System > Task` tree of 109 activities, then closes the 11 old ones.

See [`structure.md`](structure.md) for the full target tree and the exact list of
what gets closed. Files live in [`out/`](out/), generated by [`build.py`](build.py).

---

## Short answer: yes, CSV import works — but not as one file

ProjeQtor imports activities from CSV (`Tools > Import`, or the Import button on
the Activities list). The rule is simply: **row has an `id` → that record is
updated; no `id` → a new record is created.** So one file can create the new tree
and another can close the old activities.

The catch is the hierarchy. **ProjeQtor recalculates WBS on import**, so a `wbs`
column cannot express parent/child — the link is the `idActivity` column, which
wants the parent's **numeric id**. Those ids do not exist until the parent rows
have been imported, so creation runs in three passes with an export in between:

```
01_create_countries.csv   ->  export Activities  ->  02_create_systems.csv
02_create_systems.csv     ->  export Activities  ->  03_create_tasks.csv
```

Name-based parent linking is not an option here: `SAP E01` would be ambiguous
across Italia / Francia / España / Marruecos, and a 5th `SAP E01` (id 519)
already exists in Collections today.

resolves to two different ids.

## Files

Every file goes in through `Tools > Import` with **element type = `Activity`** and
**file format = `csv file (comma separated)`**. Not `Task` (that is an activity
*type*, carried in the `activity type` column, not a separate element in that
dropdown), not `Milestone`, not `Meeting`, and **not `Project`** — the countries
and systems are activities, not sub-projects.

The `comma separated` label is a misnomer: ProjeQtor's CSV reader expects `;`,
which is what these files use and what its own exports produce. Confirmed on this
instance — the smoke test parsed into the right columns and returned
`Activity #524 inserted`.

| File | Rows | Element type | Purpose |
|---|---|---|---|
| `00_smoke_test_one_activity.csv` | 1 | Activity | Import this first. Creates `Italia` only — proves the column format is accepted before you touch 109 rows. |
| `00b_test_auto_assign_column.csv` | 1 | Activity | Proves the `automaticAssignment` column name. Has an `id`, so it **updates** activity #524 rather than creating anything — watch the toggle flip on its Progress tab, then re-import with the value set back to `0`. |
| `01_create_countries.csv` | 5 | Activity | Italia, Francia, España, Portugal, Marruecos — no parent. |
| `02_create_systems.csv` | 14 | Activity | SAP E01 / PP2 / PER / P02 / GP1 / Navision, `idActivity` = country id. |
| `03_create_tasks.csv` | 90 | Activity | The leaf activities, `idActivity` = system id. |
| `04_close_old_collections.csv` | 11 | Activity | Sets the 11 existing activities to the closed status. Has an `id` column, so it **updates**, never inserts. |

Files `02` and `03` ship with `<<Italia>>` / `<<Italia > SAP E01>>` placeholders in
`idActivity`. They are deliberately **not importable** in that state — re-run
`build.py --export` to fill in the real ids.

`build.py --export` also **leaves out anything the export already contains**, so
the files only ever hold what is still missing. Re-running a pass cannot create
duplicates, and an interrupted run can simply be re-exported and resumed. It
matches nodes by WBS ancestry, not by name, so the four different `SAP E01`
branches never get confused with each other.

Encoding is **Windows-1252**, delimiter `;`, CRLF — matching your own ProjeQtor
export. If `España` lands as `Espa?a`, re-save as UTF-8 and re-import that row.

## Runbook

Create first, close second — so nobody loses a place to book time mid-cutover.

**0. Smoke test.** `Tools > Import` → element type **`Activity`**, file format
**`CSV`**, file `00_smoke_test_one_activity.csv`. If it is rejected, fix the column
format once (see *Reference ids* below) rather than 109 times. If it succeeds,
delete the `Italia` it created, or skip step 1's first row.

**1. Countries.** Import `01_create_countries.csv` (element type `Activity`) → 5
new activities under Collections. If the smoke test already created `Italia`,
re-run `build.py --export` first and the file drops to the 4 that are missing.

**2. Re-export.** Activities list → filter to project `Collections` → export to CSV.

**3. Systems.**
```bash
python3 build.py --export /path/to/export_Activity_<date>.csv
```
`out/02_create_systems.csv` now carries real country ids. Import it.

**4. Re-export again** and re-run the same command. `out/03_create_tasks.csv` now
carries real system ids. Import it.

Steps 2–4 are the same two commands repeated, and each rebuild only emits what is
still missing — so if a pass half-fails, re-export and run it again rather than
hand-editing anything. `build.py --export` on a finished tree prints
`still to create: 0 countries + 0 systems + 0 tasks`, which is the signal that the
structure is complete and you can move to step 5.

**5. Verify** the tree in ProjeQtor before closing anything. WBS should read
`2.2.12`, `2.2.12.1`, `2.2.12.1.1`, … (the old activities still hold `2.2.1`–`2.2.11`).

**6. Close the old ones.** Import `04_close_old_collections.csv`.

**7. Allocations** — resources are allocated to the *project*, not to activities,
so allocations on project 14 carry over untouched. Nothing to redo.

## Team assignment

Each activity has an **automatic assignment of the project team** toggle on its
Progress tab. With it on, every resource allocated to the project is assigned to
that activity, and the assignment list re-syncs whenever an allocation changes —
so nobody has to be assigned by hand, and new joiners are picked up automatically.
Confirmed on this instance: switching it on assigned the whole Banking team.

### Does a child inherit its parent's assignments? — UNTESTED

The docs say the toggle assigns the team to "a given activity" and describe the
dynamic part as tracking **project-team** changes, not sub-activities. That reads
as no inheritance, but it is inference and has not been tested.

It is worth settling, because it changes the amount of manual work by an order of
magnitude:

| If a child inherits | then |
|---|---|
| yes | toggle **14 systems** by hand (or maybe just the 5 countries, if it cascades further) and the 90 leaves follow |
| no | the toggle has to be set on all **90 leaves** individually |

`00e_test_child_inherits_assignment.csv` probes it: one child created under
Francia **#525**, which currently has the toggle on and 25 assignments from a
manual UI toggle. Open the new activity's Progress tab —

- **25 resources** → inheritance works. Toggle the systems (or countries) by hand
  after `02`, and `03` needs nothing.
- **0 resources** → no inheritance, confirmed rather than assumed.

Delete the test activity afterwards. Run this **before** deciding what to do about
the leaves — and before clearing #525 with `00d`, since the probe needs #525's
toggle left on.

### It cannot be set by import — tested, both paths

`automaticAssignment` is a valid import column (preview header
`[colAutomaticAssignment]`, bracketed only because the field has no display
label), and it does write the flag. What it does **not** do is generate the
assignment rows:

| Test | Result | Toggle | Assignments |
|---|---|---|---|
| `00b` — update #524 with `=1` | `Activity #524 updated` | on | **0** |
| `00c` — create #529 with `=1` | `Activity #529 inserted` | on | **0** |
| toggled by hand in the UI on #525 | — | on | **25** |

Copying the project allocations into the assignment table is work the UI control
does when you flip it; the importer takes the plain save path and writes the
column only. Create and update behave identically, so recreating an activity with
the flag pre-set does not help.

**The column is therefore left out of the files.** Keeping it would leave 90
activities displaying "automatic assignment of the project team" as ON while
nobody is assigned — worse than off, because it reads as done. `build.py` has
`AUTO_ASSIGN_COLUMN = None`; set it back to `"automaticAssignment"` only if a
later ProjeQtor version fixes this.

### Assignments ARE required here — confirmed

Activity **#80 `Sap P02`** (Collections, wbs 2.2.1) carries the toggle **on** with
all **25** resources, and real hours booked per person (Francisco Javier 105,25 h,
Carlota 16,50 h, Cristina 3,00 h, ...). Every resource shows `assigned (h) = 0`,
which is why the export reports `assigned work = 0,00` across all 477 activities
while real work totals ~41 975 h: the instance uses assignments purely as
"who may book against this", never for planning.

So the existing Collections activities are auto-assigned to the whole team, and
the 90 new leaves need the same treatment or nobody will be able to report time
against them.

### Getting the 90 leaves assigned

- **Toggle the 90 leaves by hand.** Tedious, but it stays live — the assignment
  list re-syncs whenever an allocation changes, so new joiners are picked up.
- **Import `Assignment` records** (its own element type in the same dropdown).
  25 resources x 90 leaves = 2 250 rows, nothing for a CSV, but it is a static
  snapshot that will not follow team changes. Needs the resource list and the
  column names from the `?` button with `Assignment` selected.

## Reference ids you must confirm

`build.py` defaults to `--mode labels`, which uses the column headers and values
exactly as they appear in your own export (`activity type` = `Task`, `status` =
`recorded`, `planning mode` = `as soon as possible`). ProjeQtor's own exports are
documented as re-importable, so this needs no id lookups.

If the smoke test rejects those headers, switch to technical DB field names —
`--mode ids` emits `name;idProject;idActivity;idActivityType;idStatus;idActivityPlanningMode`.
That mode needs four instance-specific numbers, filled in at the top of `build.py`:

| Constant | What to look up | Notes |
|---|---|---|
| `ID_ACTIVITY_TYPE_TASK` | id of activity type `Task` | all 477 activities in your instance use this one type |
| `ID_ACTIVITY_PLANNING_MODE_ASAP` | id of `as soon as possible` | all 477 use this one mode |
| `ID_STATUS_NEW` | id of status `recorded` | 475 of 477 activities sit here |
| `ID_STATUS_CLOSED` | id of the closing status | **not present in the export** — no activity is currently closed, so confirm the exact name on the Administration status list |

`build.py --mode ids` refuses to run until they are set, rather than emitting a file
with blanks.

## Things worth knowing before you run it

- **`Training` sits under every system**, once each — 14 of the 90 rows in
  `03_create_tasks.csv`, always the last task of its system. It is not in
  `Time_Pro.md`; it lives in `COMMON_TASKS` in `build.py`, so anything else that
  should exist everywhere goes in that one list and lands under all 14 systems.
- **No activity in your instance currently uses a parent.** All 477 are flat. This
  is the first hierarchical activity tree in the instance — worth eyeballing how
  the timesheet picker renders 3 levels before rolling it out to the team.
- **Closing is status-driven.** ProjeQtor derives the `closed` / `closed date`
  flags from the status, so `04` sets the status and lets ProjeQtor do the rest.
  If the import is rejected on a status-transition rule, close in two hops:
  `recorded → done`, then `done → closed`.
- **Close order.** `04` is sorted by descending id. ProjeQtor errors when a parent
  is closed before its children; all 11 are flat today, so this is belt-and-braces.
- **Left work is 0,00 on all 11**, so closing them will not strand any planned
  effort. Real work already booked (169,26 h on `Sap P02`, and so on) stays on the
  closed activities and remains in reports.
- **The old activities are closed, not deleted.** History and reported time are
  preserved; they simply stop accepting new entries.
- **Rollback.** If the create passes go wrong, delete the new activities (they are
  contiguous ids above 523) and re-run. To reopen the old ones, re-import `04`
  with the status column set back to `recorded`.
