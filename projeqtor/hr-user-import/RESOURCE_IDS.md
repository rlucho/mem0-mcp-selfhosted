# Where the resource ids come from

Answering: *"how will our macro know the id from resources? Can we keep a list
that auto-increments, so if the last resource is 100 the next one is 101?"*

## Short answer

A resource list in the workbook: **yes, and it's the right idea.**
Auto-incrementing it: **no — and it is the one change that could do real damage.**

## Why counting up is not safe

ProjeQtor assigns the id server-side, on INSERT. The workbook is not the only
thing writing to that table, and it never sees the result unless it re-reads.

* **Ids are not contiguous.** Deleting a record burns its id permanently. This
  instance already shows it: `Payment Run Issues` #636 was deleted and #635
  stayed; the FR > PER tasks landed at #812 after a gap.
* **Anyone else can take the next id.** Another admin creating one resource in
  the UI shifts every subsequent guess by one, silently.
* **A part-failed import still commits.** `max_execution_time` killed the 1825-row
  assignment import after ~half the rows — those ids were consumed.

And a wrong guess is not a harmless miss. **A Create row must carry no `id`.**
Writing an invented id onto a Create row does not create anything — it turns the
row into an UPDATE of whoever already holds that id, overwriting a real person's
team, capacity and role with the new hire's. The blank `id` on a create row *is*
the safety mechanism; auto-incrementing removes it in exchange for nothing,
because **inserts never needed an id in the first place.**

Only Update rows need one, and for those the id already exists on the server —
so it can be read rather than invented.

## What replaces it: the list, fed by export

[`ResourceLookup.bas`](ResourceLookup.bas) — two buttons.

**`RefreshResourceList`** — pick a ProjeQtor Resource export, and a `Resources`
sheet is rebuilt from it: `id | userName | name | team`. Columns are located by
header label, not position, because the export's column order follows whichever
fields are on display. It reports the row count, the highest id seen, and any
`userName` appearing twice.

**`FillResourceIds`** — fills column P of `Users Import` by matching `userName`.
Matched rows get the id. **Unmatched rows are left blank on purpose** — blank
means INSERT, which is the correct answer for someone who does not exist yet.
It reports matched / left-blank / ambiguous, flags any hand-typed id the export
disagrees with, and names any row marked `Update` that it could not resolve
(those are the rows `GenerateProjeQtOrCSVs` will skip).

### Matching on `userName`, not the real name

Of 214 resources, **55 carry a double space** in the real name
(`Francisco  Manzanilla`) which HTML collapses on screen — a retyped name looks
identical and is not. Another **11** are spelled in ways proper-casing destroys
(`Silvia De la Fuente Peña` → `De La`, `Cristina Garcia-Rojo Martorell` →
`Garcia-rojo`). `userName` is unique, ASCII, and is what people log in with.

## The round trip for a new hire

```
1. RefreshResourceList         current export
2. FillResourceIds             new hires stay blank -> they will INSERT
3. GenerateProjeQtOrCSVs       import import_hr_new_resources.csv
4. export Resource again  ->   RefreshResourceList
                               the new hires now have their REAL ids
5. import_allocations_by_name.csv   (created rows, keyed by name)
   import_allocations_by_id.csv     (update rows, keyed by id)
```

Step 4 is what the user described as the list "keeping itself updated" — the
difference is that it learns the ids instead of predicting them. One extra
export per HR run, and it can never be wrong.

Allocation files still come in two flavours because a resource created in the
same run has no id yet. Import the by-name file **straight after** the resource
file, while the names still match exactly what was just written.
