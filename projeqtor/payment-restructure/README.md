# Banking > Payment (project 9) restructure — ProjeQtor V11.1.3 CSV import kit

Brings the 8 Payment sub-projects up to the target task list, and gives IB, UK and
FR the system level they are missing.

Files live in [`out/`](out/), generated by [`build.py`](build.py). Sibling kit:
[`../collections-restructure`](../collections-restructure) — read its README for
the import mechanics, which are identical and already proven on this instance.

## This is not the Collections problem

Collections had **one** project (14) whose whole `Country > System > Task` tree had
to be created from nothing. Payment already has its top level: **PS, BE, IT, DE,
IB, UK, FR and PMS-TMS are sub-projects of Payment**, not activities.

| | Collections | Payment |
|---|---|---|
| Top level | activities to create | **sub-projects, already there** |
| Parent link | `idActivity` = parent activity | `idProject` = the sub-project, `idActivity` **empty** |
| To create | 109 | **97** |
| Existing rows in the way | 11 | **18** (and only under IB/UK/FR) |

So most tasks need no parent activity at all — they sit directly in their project,
which is exactly how the 53 activities already under wbs `2.1.*` are arranged.

## Files

Element type **`Activity`**, file format **`csv file (comma separated)`** — which
is `;` delimited, as on the Collections side. Rows without an `id` **insert**;
rows with one **update**.

| File | Rows | Purpose |
|---|---|---|
| `00_smoke_test_one_task.csv` | 1 | One row of `01`. Import first — proves the shape is accepted before 25 rows go in. |
| `01_add_missing_tasks_flat.csv` | 25 | The 5 missing tasks × PS, BE, IT, DE, PMS-TMS. No parent, no export needed. |
| `02_create_systems.csv` | 6 | P02 + PER (IB), P02 + Navision (UK), P02 + QUALIAC (FR), directly under their project. |
| `03_create_tasks_under_systems.csv` | 66 | 11 tasks × 6 systems. `idActivity` = the system's id, so it needs an export first. |
| `04_close_superseded_flat.csv` | 18 | The flat tasks under IB/UK/FR. **HELD — see below.** |

`03` ships with `<<IB > P02>>` placeholders and is deliberately **not importable**
until `build.py --export` fills in real ids. `build.py` also refuses to overwrite a
file that already carries resolved ids, so regenerating one file cannot destroy
another's only record of which system each task was attached to.

Every file is driven by `EXISTING`, not by a count, so re-running after a partial
import emits only what is still missing — a pass cannot create duplicates.

## Runbook

**1. Smoke.** Import `00_smoke_test_one_task.csv` → one `Payment Run Issues` under
PS. If it lands, the shape is right.

**2. Flat tasks.** Import `01_add_missing_tasks_flat.csv` (24 remaining rows, or
re-run `build.py` after updating `EXISTING` to drop the smoke row). PS, BE, IT, DE
and PMS-TMS are then complete at 11 tasks each, and **that half of the job is
done** — it does not depend on anything below.

**3. Systems.** Import `02_create_systems.csv` → 6 new activities under IB, UK, FR.

**4. Re-export** Activities, then:
```bash
python3 build.py --export /path/to/export_Activity_<date>.csv
```
`out/03_create_tasks_under_systems.csv` now carries real system ids. Import it.

**5. Verify** before closing anything: IB/UK/FR should each show 2 systems with 11
tasks under each, at wbs `2.1.5.x.y` and so on.

**6. The 18 superseded tasks** — decide first, see below.

## The 18 flat tasks under IB, UK, FR — a decision, not a step

Once IB/UK/FR have `P02 > Payment Run` etc., the old `Payment Run` sitting directly
under the project has no place in the target shape. Two ways to handle it, and they
are not equivalent:

**Close them** (`04_close_superseded_flat.csv`). Matches what Collections does.
They keep their booked hours as history and drop off timesheets. But the record
then splits: hours before the cutover on one activity, hours after on another.

**Re-parent them under `P02`** instead — set `idActivity` to P02's id on each of
the 6. History stays on one continuous activity, and P02 then needs only the 5 new
tasks rather than all 11. The catch: it asserts the existing work *was* P02 work,
and for IB/UK/FR that is a real claim — some of it may have been PER / Navision /
QUALIAC. Splitting it correctly is not something the export can tell us.

**`04` is generated but not recommended blindly, and there is no re-parent file
yet** — say which way and it is a one-line change. Nothing else in the kit depends
on this, so steps 1–5 can go in first either way.

Note also: closing is currently **blocked instance-wide**. The Collections kit hit
`the workflow does not allow you to move this item to this status` moving
`recorded -> closed`, and `idle` turned out not to be writable through the import.
Whatever unblocks it there unblocks it here. See
[`../collections-restructure/README.md`](../collections-restructure/README.md).

## Team assignment

Same Banking team as Collections. The assignment mechanics are settled there and
carry over unchanged: `automaticAssignment` as an import column does not work,
assignments do not inherit from a parent, and the working route is importing
`Assignment` records with `idProject;refType;refId;idResource;rate` and
`refType = Activity`.

`../collections-restructure/build_assignments.py` generates those from a Resource
export and takes `--leaf-ids`, so it can target these activities once they exist —
its roster logic is not Collections-specific. Assignments are per activity, so all
97 new activities need them; allocations are per project and carry over untouched.

One thing to check first, which does not apply on the Collections side: the 6
existing tasks in each project already have assignments, so only the **new** rows
need them. Feed the existing set through `--imported` to avoid duplicating.
