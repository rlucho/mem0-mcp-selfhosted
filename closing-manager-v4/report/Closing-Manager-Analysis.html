Bottom line. This is a tightly environment-coupled desktop automation — an SAP-GUI screen-scraper wired to PDFCreator and a bundled PDF merger. It runs cleanly only on a Windows PC, on the corporate network, with SAP open, from a local folder. It is not safe to run from OneDrive/SharePoint, and it carries a silent drive-selection defect that breaks printing on any PC with a D: drive.

01 What the file is

A Capgemini “Closing Manager” built for International Paper’s Record-to-Report month-end close. It drives SAP to pull data, post entries, print statutory reports to PDF, and file a single merged closing report per cost centre.

It is an RPA-style screen-scraper, not an API integration: it remote-controls a live SAP GUI window by element ID, exports data as flat files, parses them back into worksheets, and prints through the desktop PDF stack. The _changed_v3 build has most of the old SharePoint tracker calls commented out — it now leans on the workbook’s own sheets plus a prompt for the SAP user.

02 How it works — the run pipeline

Three entry points: UpdateData (refresh master data), RunClosing (the close), and CombinePDF (merge). A close proceeds through:

  1. Attach to SAP Common.SAPsess()Grabs an already-running, already-logged-in SAP session via GetObject("SAPGUI"). No session → sets config!B1="Yes" and aborts with “You are not logged in SAP.”
  2. Extract from SAPDrives transactions (SE16 table dumps T001/ZCCOD/SKB1, reports ZGLRME/ZGE132/AA02…) and saves each as a fixed-name .txt/.csv into the workbook’s own folder.
  3. Parse back inADODB.Stream reads each export; a custom pipe-delimited parser loads values into sheets, then Kill deletes the temp files.
  4. Post & report Postings.basPosts closing entries and runs the reporting transactions back in SAP, again by scripted screen IDs.
  5. Print to PDF Printing.basSets SAP’s front-end printer to the OS printer named PDFCreator, launches PDFCreator.exe, and waits for each PDF to land in \pdf\final\.
  6. Merge GiosPSMC.exeShells out to a bundled command-line tool to concatenate the per-report PDFs into one file.
  7. DeliverMoves the merged report to C:\_Files to Transfer\MONTH END CLOSE\<year>\<mm>\ under a dated name (historically also to a network share / SharePoint list).

03 Points of failure

Ranked by how likely they are to stop a real run. “Defect” = a bug in the code; “Dependency/Environment” = a precondition the code assumes.

#Failure pointSeverityWhat happens & when
1Working-drive split-brainDefectHIGHCreatePaths picks D:\ if a D: drive exists, but RunClosing hard-codes folder creation on C:\. On any PC with a D: drive, folders + the merger tool are created on C: but read from D: → print & merge fail silently.
2Run from OneDrive / SharePointEnvironmentHIGHFPath = ThisWorkbook.Path becomes an https://… URL when the file is cloud-hosted. SAP’s download dialog, ADODB.Stream file I/O and Kill all reject URLs → the run dies at the first export.
3SAP not open / not scriptableDependencyHIGHGetObject("SAPGUI") needs SAP GUI running, logged in, with scripting enabled client- & server-side. It also binds only the first connection/session — the wrong window if several are open.
4Brittle hard-coded SAP screen IDsFragilityHIGHHundreds of .findById("wnd[1]/usr/…") calls with almost no error handling. Any SAP version/theme change, altered transaction variant, or unexpected pop-up halts the macro mid-run and leaves orphaned temp files.
5PDFCreator dependencyDependency + DefectHIGHNeeds PDFCreator installed with the OS printer named exactly PDFCreator. If absent, SetPDFCreator Shell-launches the (x86) path without checking it exists → run-time error. Version drift changed the registry behaviour (now commented out).
6Fixed network share / VPNDependencyMEDIUMThe merger tool is copied from — and reports archived to — \\pl-krabpo-fsc01\ipa$\R2R\…. Off-network/off-VPN, the tool can’t be fetched (if not already local) and archiving fails.
7Legacy SharePoint SOAP endpointDependencyMEDIUMActive calls hit troom-x.capgemini.com/…/_vti_bin/Lists.asmx (SharePoint-2010 SOAP) using Windows auth + Environ("username"). If that on-prem site is retired, the calls error or silently no-op.
8Unbounded wait loopsRobustnessMEDIUMPDF steps poll with Application.Wait and no timeout. If SAP or PDFCreator stalls, Excel hangs indefinitely with no way out but to kill it.
9Infinite loop on report name clashDefectLOWIn CombinePDF the de-dup loop sets FName = …&fN but never increments fN. If both the base name and its -1 variant already exist, the loop spins forever.
10Stale temp files after a crashRobustnessLOWFixed-name exports (t001.txt, zglrme.txt, CC.csv…) are Killed at the end. A prior crash leaves them behind; the next run may read stale data.

Also noted (code-smell, no runtime impact): FShared is computed inside CreatePaths but, being undeclared, is procedure-local and never used elsewhere; the project runs without Option Explicit, so typos in variable names fail silently.

04 Your questions, answered

Does the macro need fixed folder paths?

YesSeveral. Two are hard-coded absolutes and two are UNC shares; one is relative to the workbook:

  • C:\_Files to Transfer\MONTH END CLOSE\<year>\<mm>\ — final report (always C:).
  • C:\pdf\{temp,merger,mergedFiles,printed,final}\ (or D:\pdf\…) — PDF working area.
  • \\pl-krabpo-fsc01\ipa$\R2R\…\GiosPSMC.exe — source of the merger tool.
  • \\pl-krabpo-fsc01\ipa$\R2R\…\CLOSING REPORTS\… — archive share.
  • Relative: the workbook’s own folder (ThisWorkbook.Path) — the SAP export scratch area, which must be a real filesystem path.

Does it need a file in a given folder, with a fixed name?

YesTwo executables and a set of fixed-name working files:

  • GiosPSMC.exe at <drive>\pdf\merger\ — auto-copied from the share if missing; if the share is unreachable and it isn’t already there, the merge dies.
  • PDFCreator.exe under C:\Program Files\PDFCreator\, printer named PDFCreator.
  • Fixed-name SAP exports created at runtime: t001.txt · zgxmit.txt · skb1.txt · CC.csv · PC.csv · zglrme.txt · aa02.txt · zge132.txt · DocL.csv · DocG.csv …
  • The workbook’s own config (cost centre in B2) and SAP config sheets must be populated.

What are the requirements to run it?

A Windows desktop that meets all of the following:

  • Windows + desktop Excel (Windows), macros trusted
  • SAP GUI for Windows — logged in, scripting enabled
  • SAP authorisations for the driven transactions
  • PDFCreator installed; printer named PDFCreator
  • Corporate network / VPN (UNC shares + SharePoint)
  • Local write access to C:\
  • COM: ADODB, MSXML2, Scripting, WScript.Shell
  • Runtime input: SAP user + cost centre in config!B2

Windows-desktop only — it will not run on Mac Excel or Excel for the web.

Can it run locally, or is OneDrive / SharePoint OK?

Local onlyRun it from a plain local folder. When the workbook is opened from a OneDrive/SharePoint (cloud) location, ThisWorkbook.Path returns an https://… address instead of a drive path — which breaks the SAP download dialog, the ADODB.Stream reads/writes and the Kill cleanups simultaneously. Even a locally-synced OneDrive folder is risky: AutoSave can still surface a URL path, and the constant create/delete of temp files causes sync churn and file-locking. The other fixed paths (C:\pdf, the shares) are absolute and unaffected — the only “where can the file live” constraint is that its own path must resolve to a genuine local filesystem folder.

▶
The one non-obvious trap for operators: the D: split-brain defect (#1). A machine that happens to have a D: drive will create the PDF folders and merger on C: but look for them on D:, so the close appears to work right up until printing produces nothing — with no error. This is fixed in the V4-CIO build below.
