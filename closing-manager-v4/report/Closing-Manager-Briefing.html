Decision Brief

Can we run the month-end Closing Manager on our own?

A plain-language look at what this Excel macro does, what it depends on, and the two outside systems we should cut loose to make it fully ours.

The short answer

Almost — and the gap is smaller than it looks. The macro's real work (driving SAP, printing and merging the reports) already happens on the user's own PC. But it still reaches out to two Capgemini-hosted systems for settings, logging and one small program. Neither holds anything we couldn't own ourselves, so both can be brought in-house.

1What it does

An Excel VBA macro that runs the month-end close end to end:

  • Drives SAP via SAP GUI Scripting — runs the closing transactions (SE16 table extracts, ZGLRME, ZGE132, AA02, ZGLGWUL and others), exports the data to flat files, reads it back into the workbook and posts the closing entries.
  • Creates the PDFs — sets SAP's front-end printer to PDFCreator and prints each report out to \pdf\final\.
  • Merges the PDFs — calls GiosPSMC.exe to concatenate the report set into one pack, then files it as <CC> Closure <MM> <YYYY>.pdf under C:\_Files to Transfer\MONTH END CLOSE\.
  • Reads and writes configuration over SOAP to a Capgemini SharePoint site — the subject of this review.

One design point drives most of the fragility: SAP is driven by screen element ID, not through a BAPI or other interface. The macro is a screen-scraper, so it is sensitive to SAP UI changes, unexpected pop-ups and authorisation differences.

2What it depends on

Five things must be in place. The colour tells you who controls it.

Capgemini SharePointNot ours

A Capgemini intranet site that stores the macro's settings tables and receives a log of every close we run. The macro reads its configuration from here at the start, and writes activity records back during the run.

https://troom-x.capgemini.com/sites/InternationalPaper/r2a/_vti_bin/Lists.asmx

Why it matters: if Capgemini retires this site, or we come off their network, the macro quietly loads no settings — it does not show an error. It also means our closing activity is recorded on a vendor's system.

Capgemini Poland file serverNot ours

A network drive at Capgemini's Kraków site. The macro copies one small program from it — GiosPSMC.exe, the tool that merges the individual PDFs into a single report.

\\pl-krabpo-fsc01\ipa$\R2R\R2R - IP EU GL West\USEFUL\pdf\merger\GiosPSMC.exe

Why it matters: this is only a file copy, and only the first time. Once the tool sits on the PC, the server is not needed again — so this dependency is easy to remove permanently.

SAPOurs / business-critical

The macro needs SAP already open and logged in on the same PC, with SAP's scripting option switched on.

Not a problem to solve. SAP is the source of the numbers — this dependency is legitimate and stays.

PDFCreator on the PCOurs to install

Free third-party software that turns SAP's print output into PDF files. The printer must be named exactly PDFCreator.

Under our control — a standard desktop install, no external server involved.

Local folders on the PCOurs

Working folders under C:\pdf\ and the finished report in C:\_Files to Transfer\MONTH END CLOSE\. The macro also writes temporary files next to the workbook itself.

Under our control — but note the workbook must sit in a normal local folder. Running it from OneDrive or SharePoint breaks it (explained in section 4).

This is the crux of the independence question, so it is worth being specific. It is not accounting data — it is configuration and an activity log:

One point to raise with Capgemini

Our close failures are logged to their system. When one of three checks fails (ZGE132 posting, GTB1, ZGE1174) the macro writes the Windows user name, company code, period, timestamp and an error note into ClosingTracker on their SharePoint, and UpdateData logs every run. Routine successful closes are not logged — those calls are commented out. Confirm this is agreed, who can access it, and the retention.

Encouraging sign: whoever produced this "v3" version was already heading this way. Several SharePoint calls have been switched off in the code — including the lookup that used to fetch the user's SAP ID, now replaced by simply asking the user. The decoupling has started; it just was not finished.

5Preflight Check — can users run it on its own?

Yes. It runs standalone, and it changes nothing.

PreflightCheck is a self-contained macro added in V4 specifically so users can verify their environment before committing to a close. It does not start the close, does not touch SAP beyond detecting whether a session exists, creates no folders, and writes no files. It is safe to run at any time, as often as needed.

How to run it: press Alt + F8, select PreflightCheck, click Run. It appears in the macro list automatically. For everyday use, add a button on the START sheet (Developer → Insert → Button) and assign it to the same macro.

It reports on all six preconditions in one dialog:

CLOSING MANAGER  -  PREFLIGHT CHECK

This turns every dependency in section 2 into a plain pass/fail before anyone starts a period close — including whether the network-hosted merge utility is still needed on that machine.

6How we become fully self-sufficient

In rough order — each step stands on its own, so they can be done one at a time.

  1. Take a permanent copy of the PDF merge tool Copy GiosPSMC.exe off their share and keep it somewhere we own — or deploy it with the workbook. This removes the Kraków file-server dependency outright, and is the quickest win. Worth confirming with Capgemini what the tool is and how it is licensed before we redistribute it.
  2. Ask Capgemini to export the four settings tables Request a current export of CCCrossList, ClosingVariants, ProfitCenters and ClosingTracker, plus confirmation of who maintains them today and how often they change. This tells us exactly what we are taking over.
  3. Decide where those settings should live Two sensible options: hold them in hidden worksheets inside the workbook (simplest, no server at all), or move them to a list on our SharePoint. Choice depends on how many people need to edit them and whether we want an audit trail.
  4. Repoint or switch off the SharePoint calls The V4 version already puts the address in a single named setting (CM_SP_BASE), so re-pointing it to our own site is a one-line change rather than a hunt through the code. Turning the logging off entirely is also straightforward.
  5. Make failure loud instead of silent Add a check that the settings actually loaded, so a dead endpoint stops the run with a clear message rather than closing the books on stale or empty configuration. This is the most important safety fix on the list.
  6. Clarify ownership and support of the macro itself The code names an owner and a reviewer on a Capgemini governance register. If this automation is becoming ours, we need the source, the right to change it, and a named person who supports it.
Already delivered in the meantime: a hardened V4-CIO version of the workbook fixes the D:-drive bug, blocks running from OneDrive, stops the macro hanging forever if a step stalls, and adds a one-click Preflight Check that tells the user whether SAP, PDFCreator, the folders and the network are all in place before they start a close. It also gathers the two external addresses into named settings, so the work above becomes a configuration change rather than a code rewrite.

Where this leaves us

Nothing in this automation genuinely requires Capgemini's servers. What lives there is configuration we should own anyway and a log of our own activity. The realistic path is: take the merge tool, take the settings, point the macro at our own home for them, and make it complain loudly if anything is missing. After that, the only outside system left is SAP — which is exactly as it should be.
